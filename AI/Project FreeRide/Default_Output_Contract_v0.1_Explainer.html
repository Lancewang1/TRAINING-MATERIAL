FreeRide / Intent Routing / Contract Baseline

default_output_contract v0.1

把“用户要做什么”编译成“被选中的 skill 必须交付什么”的可审计契约。

它不是一张固定回答模板，也不是第七个 route。它是路由完成之后，约束交付物、栏目、指标、呈现方式和数据状态的机器中间层。

01 / Big Picture

契约在意图解析链路中的位置

Router 先判断对象、覆盖范围和动作，再由 contract compiler 把“默认交付”和“用户额外要求”合成一个完整输出协议。垂类 skill 负责专业计算与内部 workflow，Router 不重新发明 IPT、宏观日历或回测流程。

桌面视图：从自然语言到 effective_output 的编译路径。下游 skill 只接收冻结后的交付契约和 machine spec。

    读自然语言保留原词、实体和用户明确的输出要求。

  3. 3

  4. 4

  5. 5

  6. 6
    输出 effective_output 并 handoff交给垂类 skill 或返回澄清 / fallback 状态。
02 / Dual Field

为什么要有 requested_output 和 effective_output

requested_output 只保存用户明确说出的增量；effective_output 是系统把默认契约和增量合并后，交给下游执行的完整交付协议。这样既不丢用户要求，也不会让每句话都必须重复描述 skill 的标准结果。

User explicit delta

requested_output

不负责决定 route。只记录用户额外点名的 artifact、栏目、指标或呈现。

requested_output:
  primary_artifact: null
  additional_artifacts:
    - sensitivity_table
  required_components: []
  requested_metrics: []
  presentation: []
+
Compiled delivery contract

effective_output

由 compiler 生成。包含默认交付、用户增量、共享审计 envelope 和适用的条件模式。

effective_output:
  primary_artifact: equity_model_workbook
  additional_artifacts:
    - assumption_summary
    - sensitivity_table
  required_components:
    - as_of_date
    - historical_actuals
    - ...
  requested_metrics:
    - revenue
    - fcf
  presentation:
    - workbook
    - table

四层 schema

Artifact

交付物

用户最终拿到的主要文件或结果类型。

primary_artifact
additional_artifacts
Component

必含栏目

交付物必须包含的字段、章节或审计项。

required_components
例如 catalyst_list
Metric

指标

用户明确要求计算或展示的数值口径。

requested_metrics
例如 oas、carry
Presentation

呈现方式

不改变 route，只约束结果的展示形态。

narrative · table · chart
03 / Merge Logic

编译顺序、优先级与边界

契约的价值在于可重复。相同的 route、action、resolved slot 和用户显式要求，应得到相同的输出结构；任何无法支持的部分必须显式暴露。

规则操作定义
主产物优先级用户显式值 > primary action overlay > skill base。secondary action 的主 artifact 已有主产物时追加到 additional_artifacts。
列表合并additional_artifacts、required_components、requested_metrics 做稳定去重并集，保留出现顺序。
呈现冲突兼容的 presentation 合并；互斥的显式要求进入 clarification_required，不能猜一个。
显式否定例如“不要图表”可以抑制默认项，并写入系统 trace；不新增第五层 output。
不支持输出保留用户原始请求，返回 coverage / fallback 状态；绝不静默删除或伪造数据。
次动作secondary_actions 必须是 skill 内 leaf action id。只有 family hint 时先保留 hint，不直接查 overlay。
一个重要区分：对象和 action 决定“去哪一个 skill”；contract 决定“这个 skill 至少交付哪些内容”。输出要求可以作为冲突证据，但不能反向把 NVDA 的 DCF 请求改成主题研究。

Shared output envelope

以下五项会并入 supported effective_output.required_components，与 skill 栏目稳定去重。

as_of_date结果对应的数据截止时间或事件时间。
source_trace关键事实、用户提供值、查找数据的来源。
availability_statusavailable / not_released / unavailable / not_applicable。
assumption_provenance区分 user-provided、skill-default、model-derived。
coverage_limitations覆盖边界、排除对象和不能完成的部分。

07 / Readiness

第一个用户意图解析 Skill，大致做完了吗？

要把“做完”拆成两个层次：设计契约是否闭环，以及生产运行时是否已经可用。当前前者已达到 v1 基线，后者还没有。

已完成：Intent Decomposition / Routing v1 设计层

  • 6 个正类 route + 唯一 SOFT_FALLBACK 已冻结。
  • 对象类型、scope_shape、三层 pair 结构和 partial coverage 规则已确认。
  • 8 个 global action family 已确认；共享 workflow_stage 已删除。
  • requested_output 四层 schema 与双字段合并规则已确认。
  • 6 个 default contract、共享 envelope、条件 mode overlay 已机器化。
  • 8 条 fixture 已完成编译结果断言，并通过一致性校验。

尚未完成：生产 Skill 的运行层

  • 实现真正的 contract compiler 与 provenance trace。
  • 把 router 输出接到六个垂类 skill 的输入协议和数据源。
  • 补充更大规模的自然语料、对抗样本和 owner 评审。
  • 把 fixture 回归校验接入 CI / 发布门禁。
结论：可以说“第一个 Intent Decomposition Skill 的 v0.1 设计大致完成”，但不能说生产能力已经完成。

现在已有稳定的输入边界、路由出口和交付契约；下一阶段的核心工作从“定义它是什么”转向“把它实现成可运行、可评估、可接垂类工具的 compiler”。
