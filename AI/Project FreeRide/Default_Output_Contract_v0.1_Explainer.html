01 / 一步一步

用户说一句话，我们怎样把它变成标准任务

先不用记字段名。系统先读懂这句话在说什么，再按固定顺序整理：说的是谁或什么、这些对象是什么关系、用户要做什么、应该交给哪个专业方向，最后列出必须交付的内容。

示例：用户原话
“帮我比较 NVDA、TSM 和 ASML 在 HBM → CoWoS → GPU 这条链上的受益程度，列出未来 6-12 个月的催化剂和失效条件。”

4输出要求的组成部分
8用于检查流程的示例句子
1

先把原话保留下来

不急着猜意思，也不先改写。原句会一直保留，方便之后检查系统有没有理解错。

留下：“比较……受益程度，列出催化剂和失效条件”
2

圈出研究对象

找出句子里真正要研究的名词，并标明它是什么：公司、股票、产业链节点、货币、曲线、债券或宏观数据。

对象：HBM、CoWoS、GPU；NVDA、TSM、ASML
3

看对象之间的关系

判断是一个对象、几个并列对象、两条腿的关系、传导链、曲线结构，还是几种范围放在一起。

关系：产业链传导 + 三家公司并列比较
4

找出用户要做的事

从动词判断动作：查询、画结构、比较、解释、建模、构造交易、检查风险或回测。先确定一个主要动作。

动作：主动作是画链；附加动作是比较受益者
5

选对应的专业方向

把“对象 + 动作”与六个已冻结的专业方向匹配。不是看到一个关键词就直接跳转。

方向：AI / 半导体股票主题研究
6

检查能不能接

确认对象在支持名单内，动作有对应能力，必要资料是否可用，句子有没有关键歧义。

结果：对象和动作都支持，可以继续
7

只记录用户明确点名的要求

把用户额外说出的时间范围、栏目、指标和格式单独记下；没有说的内容不冒充用户要求。

明确要求：6-12 个月、催化剂、失效条件
8

补上标准交付清单

在专业方向的默认交付上，加上用户刚才点名的内容，形成一份下游专业模块可以直接执行的任务单。

交付：产业链图 + 受益者比较 + 证据、催化剂、失效条件

桌面视图：上面的 8 步可以压缩成 6 个阶段。每一步先整理“内容”，最后才决定“交付什么”。

  1. 1
    保留用户原话不先猜，不先改写，保留原句和上下文。
  2. 2
    圈出研究对象标明是公司、股票、产业链节点、货币、曲线、债券还是宏观数据。
  3. 3
    判断对象关系区分单个、集合、两腿关系、传导链、曲线结构和组合范围。
  4. 4
    找出主要动作从“比较、解释、建模、构造、回测”等动词确定用户要做什么。
  5. 5
    选择专业方向把对象和动作匹配到六个已确定的专业模块。
  6. 6
    检查覆盖范围支持就继续；有歧义就追问；不支持就保留原要求并说明边界。
  7. 7
    记录用户明确要求单独保存时间、栏目、指标和格式等额外要求。
  8. 8
    生成标准任务并交接补齐默认交付清单，再交给对应的专业模块。

02 / 拆开看每一步

每一步到底在判断什么

下面每一栏都可以打开或收起。先看“人话说明”，再看这一栏目前允许出现哪些变量。变量是给系统用的，不要求用户一开始就会说出机器名。

1把原话保留下来 不做解释，只做记录

系统先把用户真正说的话保存下来。就像做题先抄清题目，不能一开始就凭感觉改题。后面每一个判断，都要能回到这句话找到依据。

这一栏目前支持的变量

机器名可选值 / 形式高中生能懂的意思
utterance用户原始文字用户到底说了什么，一字不偷偷改掉。
conversation_context前文，或 null如果用户说“上面那条规则”，就把前面相关内容带上。
routing_evidence原句中的关键短语指出是哪几个词让系统做出这个判断。
normalizations
normalization_trace		别名 → 标准写法例如把“DCF”记录成标准动作名，但仍保留用户原词。
confidencelevel + reasons系统有多确定，以及为什么这么判断。
这一步没有“猜一个最像的答案”这个选项。找不到依据，就把原话留下，等后面追问。
2圈出研究对象 先回答“在研究谁或什么”

把句子里的名词找出来，并给每个名词贴一个类型。股票、产业链节点、美元债和 CPI 不是同一种对象，后面能用的专业模块也不同。

3看对象之间的关系 回答“这些东西是怎么放在一起的”

三个公司放在一起，不一定就是 pair；有箭头的 HBM → CoWoS → GPU，也不是普通列表。系统要把对象之间的结构保留下来，否则后面的比较和计算会变形。

4找出用户要做的事 回答“用户想让我们做什么”

对象只是“研究谁”。动作才是“要做什么”。系统从动词和上下文判断一个主要动作，也可以记录几个附加动作，但不会因为附加动作就凭空增加新的专业方向。

03 / 两份清单

用户说了什么，最后要交付什么

系统会同时保留两份清单：一份只记录用户明确点名的内容，另一份是在此基础上补齐专业方向的标准内容。前者不替用户做决定，后者才是交给专业 skill 执行的完整任务单。

User explicit delta

requested_output

不负责决定 route。只记录用户额外点名的 artifact、栏目、指标或呈现。

requested_output:
  primary_artifact: null
  additional_artifacts:
    - sensitivity_table
  required_components: []
  requested_metrics: []
  presentation: []
+
Compiled delivery contract

effective_output

由 compiler 生成。包含默认交付、用户增量、共享审计 envelope 和适用的条件模式。

effective_output:
  primary_artifact: equity_model_workbook
  additional_artifacts:
    - assumption_summary
    - sensitivity_table
  required_components:
    - as_of_date
    - historical_actuals
    - ...
  requested_metrics:
    - revenue
    - fcf
  presentation:
    - workbook
    - table

四层 schema

Artifact

交付物

用户最终拿到的主要文件或结果类型。

primary_artifact
additional_artifacts
Component

必含栏目

交付物必须包含的字段、章节或审计项。

required_components
例如 catalyst_list
Metric

指标

用户明确要求计算或展示的数值口径。

requested_metrics
例如 oas、carry
Presentation

呈现方式

不改变 route，只约束结果的展示形态。

narrative · table · chart
04 / 如何补齐

系统怎样把默认内容和用户要求放在一起

先放入这个专业方向本来就需要的内容，再加入用户明确点名的内容。遇到冲突不猜，遇到不支持也不偷偷删掉。

规则操作定义
主产物优先级用户显式值 > primary action overlay > skill base。secondary action 的主 artifact 已有主产物时追加到 additional_artifacts。
列表合并additional_artifacts、required_components、requested_metrics 做稳定去重并集，保留出现顺序。
呈现冲突兼容的 presentation 合并；互斥的显式要求进入 clarification_required，不能猜一个。
显式否定例如“不要图表”可以抑制默认项，并写入系统 trace；不新增第五层 output。
不支持输出保留用户原始请求，返回 coverage / fallback 状态；绝不静默删除或伪造数据。
次动作secondary_actions 必须是 skill 内 leaf action id。只有 family hint 时先保留 hint，不直接查 overlay。
简单说：前面几步决定“交给哪个专业方向”；这一部分只决定“这个方向至少要交付什么”。输出格式不能把一个建模问题偷偷改成另一种研究。

每份结果都要带的五项信息

这些信息会自动加入最终任务单，方便用户知道数据从哪里来、截至哪一天、哪些地方还有限制。

as_of_date结果对应的数据截止时间或事件时间。
source_trace关键事实、用户提供值、查找数据的来源。
availability_statusavailable / not_released / unavailable / not_applicable。
assumption_provenance区分 user-provided、skill-default、model-derived。
coverage_limitations覆盖边界、排除对象和不能完成的部分。

06 / 完整走一遍

把刚才那句话从头到尾走一次

下面用同一句话演示 8 步。左边是这一格在做什么，右边是这一格留下的标准结果。每一步都只增加信息，不偷偷改变用户原意。

客户问题
“画 HBM→CoWoS→GPU 受益链，比较 NVDA、TSM、ASML，未来 6-12 个月，列催化剂和失效条件。”
STEP 1

保留原话

先不解释，只把句子和关键词存下来。

留下：HBM→CoWoS→GPU、NVDA/TSM/ASML、6-12 个月、催化剂、失效条件。
STEP 2

圈出对象

把名词分成产业链节点和股票。

object_type：industry_node = HBM、CoWoS、GPU；equity_security = NVDA、TSM、ASML。
asset_class：EQ。
STEP 3

看对象关系

箭头表示传导顺序，三家公司是并列比较；这不是一个普通列表。

subject_scope：composite。
子范围 A：ordered_chain（HBM → CoWoS → GPU）。
子范围 B：set + comparison（NVDA、TSM、ASML）。
STEP 4

找出动作

“画链”是主要动作，“比较受益程度”是附加动作。

action：family=map_structure，type=chain_map，secondary_actions=[beneficiary_rank]。
STEP 5

选专业方向

产业链 + 公司比较 + 主题研究，匹配到 AI / 半导体股票方向。

skill_id：eq_ai_semis_thesis。
next_hop：inspiration_spec。
STEP 6

检查能不能接

对象在名单内，动作有对应能力，没有需要用户补充的关键选择。

状态：route_status=routed、coverage_status=in_coverage、capability_status=supported、missing_slots=[]。
STEP 7

记录用户明确要求

只记录用户亲口说出的时间范围和必含栏目。

requested_output：required_components=[catalyst_list, invalidation_conditions]；horizon=6-12m。
STEP 8

生成完整任务

把方向默认内容、画链附加内容、比较附加内容和用户要求合在一起。

effective_output：主交付 chain_map；附加 ranking_table；必须包含证据链、节点关系、传导机制、催化剂和失效条件；文字 + 表格。

交接给专业模块时的简版任务单

skill_id: eq_ai_semis_thesis
scope: HBM → CoWoS → GPU + NVDA / TSM / ASML
action: chain_map + beneficiary_rank
horizon: 6-12m
must_include: catalyst_list, invalidation_conditions
status: compiled

这一步没有做什么

没有把三家公司压成一个对象，没有把“画链”改成 DCF，也没有在用户没要求时偷偷增加目标价或交易指令。

结果专业模块收到的是一张清楚的任务单，而不是一段需要重新猜测的原话。
