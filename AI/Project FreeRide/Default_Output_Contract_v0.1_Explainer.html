01 / 一步一步

用户说一句话，我们怎样把它变成标准任务

先不用记字段名。系统先读懂这句话在说什么，再按固定顺序整理：说的是谁或什么、这些对象是什么关系、用户要做什么、应该交给哪个专业方向，最后列出必须交付的内容。

示例：用户原话
“帮我比较 NVDA、TSM 和 ASML 在 HBM → CoWoS → GPU 这条链上的受益程度，列出未来 6-12 个月的催化剂和失效条件。”

8用于检查流程的示例句子
1

先把原话保留下来

不急着猜意思，也不先改写。原句会一直保留，方便之后检查系统有没有理解错。

留下：“比较……受益程度，列出催化剂和失效条件”
2

圈出研究对象

找出句子里真正要研究的名词，并标明它是什么：公司、股票、产业链节点、货币、曲线、债券或宏观数据。

对象：HBM、CoWoS、GPU；NVDA、TSM、ASML
3

看对象之间的关系

判断是一个对象、几个并列对象、两条腿的关系、传导链、曲线结构，还是几种范围放在一起。

关系：产业链传导 + 三家公司并列比较
4

找出用户要做的事

从动词判断动作：查询、画结构、比较、解释、建模、构造交易、检查风险或回测。先确定一个主要动作。

动作：主动作是画链；附加动作是比较受益者
5

选对应的专业方向

把“对象 + 动作”与六个已冻结的专业方向匹配。不是看到一个关键词就直接跳转。

方向：AI / 半导体股票主题研究
6

检查能不能接

确认对象在支持名单内，动作有对应能力，必要资料是否可用，句子有没有关键歧义。

结果：对象和动作都支持，可以继续
7

只记录用户明确点名的要求

把用户额外说出的时间范围、栏目、指标和格式单独记下；没有说的内容不冒充用户要求。

明确要求：6-12 个月、催化剂、失效条件
8

补上标准交付清单

在专业方向的默认交付上，加上用户刚才点名的内容，形成一份下游专业模块可以直接执行的任务单。

交付：产业链图 + 受益者比较 + 证据、催化剂、失效条件

桌面视图：上面的 8 步可以压缩成 6 个阶段。每一步先整理“内容”，最后才决定“交付什么”。

  1. 1
    保留用户原话不先猜，不先改写，保留原句和上下文。
  2. 2
    圈出研究对象标明是公司、股票、产业链节点、货币、曲线、债券还是宏观数据。
  3. 3
    判断对象关系区分单个、集合、两腿关系、传导链、曲线结构和组合范围。
  4. 4
    找出主要动作从“比较、解释、建模、构造、回测”等动词确定用户要做什么。
  5. 5
    选择专业方向把对象和动作匹配到六个已确定的专业模块。
  6. 6
    检查覆盖范围支持就继续；有歧义就追问；不支持就保留原要求并说明边界。
  7. 7
    记录用户明确要求单独保存时间、栏目、指标和格式等额外要求。
  8. 8
    生成标准任务并交接补齐默认交付清单，再交给对应的专业模块。

02 / 两份清单

用户说了什么，最后要交付什么

系统会同时保留两份清单：一份只记录用户明确点名的内容，另一份是在此基础上补齐专业方向的标准内容。前者不替用户做决定，后者才是交给专业 skill 执行的完整任务单。

User explicit delta

requested_output

不负责决定 route。只记录用户额外点名的 artifact、栏目、指标或呈现。

requested_output:
  primary_artifact: null
  additional_artifacts:
    - sensitivity_table
  required_components: []
  requested_metrics: []
  presentation: []
+
Compiled delivery contract

effective_output

由 compiler 生成。包含默认交付、用户增量、共享审计 envelope 和适用的条件模式。

effective_output:
  primary_artifact: equity_model_workbook
  additional_artifacts:
    - assumption_summary
    - sensitivity_table
  required_components:
    - as_of_date
    - historical_actuals
    - ...
  requested_metrics:
    - revenue
    - fcf
  presentation:
    - workbook
    - table

四层 schema

Artifact

交付物

用户最终拿到的主要文件或结果类型。

primary_artifact
additional_artifacts
Component

必含栏目

交付物必须包含的字段、章节或审计项。

required_components
例如 catalyst_list
Metric

指标

用户明确要求计算或展示的数值口径。

requested_metrics
例如 oas、carry
Presentation

呈现方式

不改变 route，只约束结果的展示形态。

narrative · table · chart
03 / 如何补齐

系统怎样把默认内容和用户要求放在一起

先放入这个专业方向本来就需要的内容，再加入用户明确点名的内容。遇到冲突不猜，遇到不支持也不偷偷删掉。

规则操作定义
主产物优先级用户显式值 > primary action overlay > skill base。secondary action 的主 artifact 已有主产物时追加到 additional_artifacts。
列表合并additional_artifacts、required_components、requested_metrics 做稳定去重并集，保留出现顺序。
呈现冲突兼容的 presentation 合并；互斥的显式要求进入 clarification_required，不能猜一个。
显式否定例如“不要图表”可以抑制默认项，并写入系统 trace；不新增第五层 output。
不支持输出保留用户原始请求，返回 coverage / fallback 状态；绝不静默删除或伪造数据。
次动作secondary_actions 必须是 skill 内 leaf action id。只有 family hint 时先保留 hint，不直接查 overlay。
简单说：前面几步决定“交给哪个专业方向”；这一部分只决定“这个方向至少要交付什么”。输出格式不能把一个建模问题偷偷改成另一种研究。

每份结果都要带的五项信息

这些信息会自动加入最终任务单，方便用户知道数据从哪里来、截至哪一天、哪些地方还有限制。

as_of_date结果对应的数据截止时间或事件时间。
source_trace关键事实、用户提供值、查找数据的来源。
availability_statusavailable / not_released / unavailable / not_applicable。
assumption_provenance区分 user-provided、skill-default、model-derived。
coverage_limitations覆盖边界、排除对象和不能完成的部分。

07 / 做到哪一步

现在这套流程已经完成到哪里

现在已经把“怎么拆、怎么归类、怎么生成任务单”定下来了；把它接成真正自动运行的程序，还需要下一阶段的工作。

已完成：Intent Decomposition / Routing v1 设计层

  • 6 个正类 route + 唯一 SOFT_FALLBACK 已冻结。
  • 对象类型、scope_shape、三层 pair 结构和 partial coverage 规则已确认。
  • 8 个 global action family 已确认；共享 workflow_stage 已删除。
  • requested_output 四层 schema 与双字段合并规则已确认。
  • 6 个 default contract、共享 envelope、条件 mode overlay 已机器化。
  • 8 条 fixture 已完成编译结果断言，并通过一致性校验。

尚未完成：生产 Skill 的运行层

  • 实现真正的 contract compiler 与 provenance trace。
  • 把 router 输出接到六个垂类 skill 的输入协议和数据源。
  • 补充更大规模的自然语料、对抗样本和 owner 评审。
  • 把 fixture 回归校验接入 CI / 发布门禁。
结论：可以说“第一个 Intent Decomposition Skill 的 v0.1 设计大致完成”，但不能说生产能力已经完成。

现在已有稳定的输入边界、路由出口和交付契约；下一阶段的核心工作从“定义它是什么”转向“把它实现成可运行、可评估、可接垂类工具的 compiler”。
